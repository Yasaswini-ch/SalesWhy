## 2026-10-13 (continued) -- synthetic drops, evaluation, baselines
- Built `src/inject.py` (synthetic drops with known causes), `src/detect.py` (shortfall-window finder + deterministic cause attribution), `src/eval.py` (scores detections against ground truth, builds baseline comparison). Wrote `results/eval.md` and `results/eval.csv`.
- Injected 3 of the 4 cause types from CLAUDE.md's Data section: price_increase (+15% price, -25% revenue), stockout (5 days, zero products/orders/revenue), freight_spike (+90% freight, -20% revenue). **Decision (ambiguous, logged per CLAUDE.md rule):** "promo removal" isn't a separate detectable cause since detect.py's only candidate features are price/freight/active-products — a promo ending looks identical to a price increase in the data. Treating it as a price_increase injection rather than building a 4th, fundamentally indistinguishable category. This is itself a finding worth a line in the post (the tool can't tell "price went up" from "discount ended" from sales data alone, and arguably neither could a human looking at the same CSV).
- **Three real bugs found and fixed while building the eval harness** (this took most of this stretch; keeping the detail because the failures are more interesting than the final numbers):
  1. Injecting directly into the already-smoothed `avg_price_trailing7` column instead of the raw `avg_price` diluted a 4-day price shock into noise (a 7-day rolling average mixes in ~3-6 days of unaffected history). Fixed by injecting into raw daily columns and recomputing features from scratch (`features.build_features`) afterward.
  2. Bigger bug, affected the *entire* pipeline, not just the eval: `prep.py` was filling `avg_price` with `0` on zero-order days. Average price is undefined when nothing sold that day, not zero — forcing it to 0 reads as "price crashed" to any trailing-average feature built on top, which spuriously fires the price_increase/price_drop candidate on *any* day orders happen to stop (e.g. during a stockout). Fixed: `avg_price` now forward-fills the last known price on zero-order days; revenue/freight/order counts still correctly fill to 0 (they're genuinely zero). Re-ran `prep.py` → `features.py` → `predict.py` after this fix.
  3. Injected windows were spaced only 3 days apart; detect.py's shortfall-run finder merged nearby separate injections (plus ambient prediction noise) into single giant windows (one stretch was 27 days for a single seller) and picked whichever cause happened to dominate the merged span. Fixed two ways: spaced injections 16 days apart (TARGET_PER_CAUSE_PER_SELLER dropped from 6 to 2 to still fit in each seller's ~150-180 day test window — **30 injections total per cause became 10 per cause**, logged here rather than silently changing CLAUDE.md's stated target), and capped `detect.py`'s shortfall-run length at 8 days so one noisy stretch can't swallow multiple events.
- **Current eval numbers (TabPFN pipeline):** stockout 90% (9/10), freight_spike 20% (2/10), price_increase 0% (0/10). Overall accuracy on flagged+named windows 36.7%, abstain rate 3.3%, miss rate 20%. Moving-average baseline: stockout 90%, freight_spike 0%, price_increase 0%, overall 30%.
- **Known limitation, not fully solved today:** price_increase and freight_spike attribution are weak because the candidate features have very different natural noise levels per seller — e.g. one seller's `n_active_products` naturally swings 1-3 day to day while its price sits at a near-constant 53.9, so a real-but-small price move loses to random noise in the products count when both are compared as raw percent changes. Tried normalizing by each candidate's own baseline std (z-score) to correct for this — made things worse overall (abstain rate jumped to 30-50%), reverted. Settled on raw percent-change comparison (current state) rather than keep tuning; this is an honest limitation for the write-up, not a hidden one. Likely needs either more training data per seller, better features, or accepting that cause attribution is reliable mainly for binary/high-contrast causes (stockout) and weaker for continuous ones (price, freight) on sparse data.
- Baseline (b) from CLAUDE.md's evaluation section (generic LLM asked "why did sales drop?") is deferred — no LLM API key configured in this environment. Noted in `results/eval.md`; will run once a key is available.
- "Not sure" state: implemented at the backend level in `detect.py` (`cause: "unknown"` when no candidate clears the confidence floor). UI copy for it is a Tier 1 item for the app.py work coming up next.
- Spent extra time (at user's request) trying to fix the price_increase/freight_spike weakness properly before moving on. Tried two more z-score normalization variants: (1) mean/std over a wider 60-day volatility window with a relative std floor, (2) median/MAD (robust statistics) instead of mean/std. Neither beat the plain percent-change baseline on overall accuracy (z-score variants: 0.233-0.3 overall; plain percent-change: 0.367 overall, stockout 0.9). The robust median/MAD version did lift price_increase to 0.2 but cost stockout (0.9 -> 0.7), a net loss. Reverted to the plain percent-change version (current `detect.py`) rather than keep tuning blindly without a principled reason to expect the next variant to work. Decision: ship with this known limitation, document it honestly in the write-up, and move on.

- No real seller replied to the export requests sent out earlier today. Applied CLAUDE.md's documented fallback: "No real seller replies: use a public small-shop dataset and say so plainly." Used the UCI/Kaggle **Online Retail** dataset (`vijayuv/onlineretail` on Kaggle) -- a real UK-based online gift retailer's transaction log, Dec 2010 to Dec 2011, 541,909 line-item rows. This is genuinely real sales data (not synthetic, not Olist), just not from a seller who personally replied to an outreach request. Saying so plainly here and will say so in the post.
- Deliberately did **not** preprocess this CSV before testing -- the whole point of a "real seller" test is to find what breaks on messy data the mapper/pipeline has never seen, not to hand-hold it into our existing fixture shapes. Two real bugs surfaced immediately:
  1. **Mapper picked `InvoiceNo` as the amount column.** The numeric-fallback heuristic ("largest-mean numeric column") doesn't know an invoice number isn't revenue -- `"536365"` has a bigger mean than `UnitPrice`. Fixed in `mapper.py`: numeric amount candidates whose header ends in `id/no/num/number/code` are now excluded outright, and among what's left, a column with decimal values is preferred over an all-integer one (prices have cents; ids and quantities don't).
  2. **Product column wasn't detected at all** -- the header is `Description`, which wasn't in the product hint list (which had `productname`, `title`, `sku`, etc., but not the single most common plain-English header for "what this line item is"). Added `description`, `itemdescription`, `productdescription` to the hints.
  3. **Deeper issue, not just a mapper miss:** even after fixing #1, the best amount candidate is `UnitPrice` -- a per-unit price, not a line total (unlike Shopify's `Total`, which already includes quantity). Feeding it straight into `aggregate_daily` as revenue would have silently undercounted every multi-item line. Fixed in `pipeline.aggregate_daily`: if the amount header doesn't contain "total" and a quantity column is mapped, revenue is now computed as `amount * quantity` instead of `amount` alone. This is a heuristic, not a certainty, but it's a real correctness fix that only showed up because this dataset's amount column happens to be a price, not a total -- every CSV used so far (Shopify, Etsy, Olist, the synthetic sample shop) had an already-summed total column, so this path was never exercised before today.
- With both fixes in place, ran the full pipeline end-to-end on the whole 541K-row file (no filtering, no sampling): 374 days of real daily revenue (mean ~£26k/day, genuinely messy -- some days have *negative* revenue from returns/cancellations, since the dataset includes credit-note invoices with negative quantities). Took 66.9s (TabPFN fit+predict on a much bigger training set than the synthetic sample shop). Found 15 windows: mostly `more_products` spikes clustering through November and into early December, which lines up with this being a real UK retailer's holiday shopping ramp-up -- a plausible, externally-sanity-checkable pattern, not noise. Doesn't break anything downstream (n_orders only feeds `n_active_products`'s placeholder fallback and isn't itself a model feature), but it's not literally correct and worth a caveat in the post if this dataset's order counts come up.

- **Caught a real bug in my own grading, not the LLM's output:** initial keyword list for "stockout" was `["stock", "inventory", ...]`, but the model consistently phrased its (correct!) diagnosis as "zero active products listed for sale" -- never using the word "stock." This scored as 0/10 stockout accuracy for the LLM, which would have been a materially misleading result. Caught it by actually reading the raw `llm_answer` text for every miss before trusting the aggregate number (a good habit, not an accident -- same thing that caught the earlier detect.py bugs during the eval harness work). Fixed the keyword list to include "active products" and similar phrasings; re-scored from the already-saved answers (no need to re-call the API).
- **Final result, and the most surprising number in this whole evaluation: the generic LLM (53.3% accuracy) beat SalesWhy's own deterministic pipeline (36.7%).** Breakdown: stockout 90% (tied with SalesWhy), freight_spike 40% (vs SalesWhy's 20%), price_increase 30% (vs SalesWhy's 0%). Abstain rate 23.3%, mean latency 5.47s/call, 20,866 prompt + 967 completion tokens across 30 calls.
  - This is genuinely humbling for a project whose principle #1 is "deterministic detection, LLM only phrases" -- the premise was that a raw LLM call would be unreliable/hallucinate causes, but it actually reasoned better than our threshold-and-percentage-change heuristic on the same sparse, noisy Olist data, particularly on price/freight where our pipeline struggles most.
  - But it has a different, arguably worse failure mode for user trust: several wrong answers were *confidently* wrong -- correctly noticing revenue or order count fell, then misattributing it to the proximate symptom ("a total lack of activity," "orders plummeted") rather than the actual underlying price/freight change, phrased with just as much certainty as its correct answers. SalesWhy's deterministic attribution can't do this by construction: it only ever names price, freight, or product-count as the cause, or abstains -- never "demand fell for some reason." Whether that's worth 17 percentage points of accuracy is a genuinely open question, and exactly the kind of finding worth leading with in the post rather than hiding.
